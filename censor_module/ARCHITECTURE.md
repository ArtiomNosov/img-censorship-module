# Как устроен Censor Module под капотом

Документ объясняет, что реально происходит внутри модуля, шаг за шагом. Цель —
чтобы после прочтения было понятно: какие компоненты есть, кто кого вызывает,
где принимается решение и где сейчас «дыры».

> TL;DR. Это многослойный фильтр для картинок. На вход приходит запрос
> (промпт и/или картинка), несколько независимых «сенсоров» оценивают её по
> списку запрещённых категорий, а финальный движок по порогам выдаёт вердикт
> **allow / review / block**.

> **Версия алгоритма: v2.** Конвейер сфокусирован на изображении. Активны
> визуальный zero-shot классификатор, NSFW-детектор и слой арбитров
> (ShieldGemma + консенсус-эвристика). Текстовый гард и OCR **намеренно
> отключены** на этом этапе (см. PLAN.md, P0.1) — контракты адаптеров остаются
> в коде для будущего возврата.

---

## 1. Общая картина

```
            ┌─────────────────────────────────────────────────────────┐
   HTTP /   │              GuardrailPipeline.moderate (v2)             │
   CLI      │                                                         │
   запрос ─►│  load_image(request)   (нет картинки → allow)           │
            │      │                                                  │
            │      ▼                                                  │
            │  ┌── Сенсоры (role="sensor", возвращают SignalResult)┐  │
            │  │  visual          (zero-shot по таксономии)       │  │
            │  │  explicit        (NSFW-детектор)                 │  │
            │  └──────────────────────┬───────────────────────────┘  │
            │                         ▼                               │
            │  ┌── Арбитры (role="judge") ────────────────────────┐  │
            │  │  shieldgemma     (мультимодальный судья, опц.)    │  │
            │  │  heuristic       (консенсус ≥2 сенсоров)          │  │
            │  └──────────────────────┬───────────────────────────┘  │
            │                         ▼                               │
            │                 DecisionEngine.decide                   │
            │                         │                               │
            │                         ▼                               │
            │      ModerationResponse: verdict + categories +         │
            │      confidence + evidence + signals + notes            │
            └─────────────────────────────────────────────────────────┘
```

Ключевая идея: **сенсоры ничего не решают сами**. Каждый лишь выдаёт оценки по
категориям в едином формате `SignalResult`. Всю «политику» (что блокировать, что
на ревью) держит один компонент — `DecisionEngine`. Это позволяет менять модели,
не трогая логику решений.

Сигналы делятся по полю `role` на два вида: **сенсоры** (`sensor`) — независимые
детекторы, чьи оценки участвуют в фьюжне (берётся максимум), и **арбитры**
(`judge`) — их мнение служит *подтверждением* для блокировки soft-категорий.
Движок различает их именно по `role`, а не по имени.

## 2. Формат данных — три pydantic-модели (`schemas.py`)

Весь модуль общается тремя структурами:

### `ModerationRequest` — вход
| поле | смысл |
|------|-------|
| `request_id` | автогенерируемый UUID запроса |
| `scenario` | `text2image` / `img2img_stylization` / `img2img_editing` / `output` |
| `stage` | `input` (проверка до генерации) или `output` (проверка результата) |
| `prompt` | текст промпта (опционально) |
| `image_path` / `image_base64` | картинка как путь к файлу или base64 |
| `metadata` | произвольные доп. данные |

### `SignalResult` — то, что возвращает каждый сенсор
| поле | смысл |
|------|-------|
| `name` | имя сенсора (`visual_classifier`, `policy_judge_shieldgemma`, …) |
| `status` | `ok` (отработал) / `skipped` (выключен/нет бэкенда) / `error` (упал) |
| `role` | `sensor` (по умолчанию) или `judge` — см. ниже |
| `categories` | словарь `{код_категории: оценка 0..1}` |
| `text` | извлечённый текст (для OCR, в v2 не используется) |
| `reason` | человекочитаемое пояснение |
| `raw` | сырой вывод модели для отладки |

> Поле `role` отделяет независимые детекторы (`sensor`) от арбитров (`judge`).
> Оценки сенсоров фьюзятся максимумом; арбитры дают подтверждение, без которого
> soft-категория не блокируется (см. раздел 6).

> Только сигналы со `status == "ok"` участвуют в голосовании. `skipped`/`error`
> не валят запрос — их причина просто попадает в `notes` ответа. Это и есть
> «мягкая деградация»: нет модели → сервис всё равно отвечает.

### `ModerationResponse` — выход
`verdict` (allow/review/block), `categories` (что сработало), `confidence`
(макс. оценка по сработавшим категориям), `reason`, `evidence` (какие сенсоры
подтвердили каждую категорию), `signals` (все сырые сигналы), `notes`.

## 3. Таксономия нарушений (`taxonomy.py`)

11 категорий, у каждой есть флаг `hard_block`:

**Hard-block (блокируются от любого сенсора):**
`sexual`, `violence_gore`, `self_harm`, `hate_extremism`, `illegal_activity`,
`shocking`.

**Soft / review (блокируются только если подтвердил policy judge):**
`harassment`, `deception_fraud`, `political_persuasion`,
`health_misinformation`, `spam_scams`.

Из этого списка автоматически строятся вспомогательные структуры:
- `VISUAL_LABELS` — текстовые описания категорий, которые скармливаются
  zero-shot классификатору в качестве вариантов ответа;
- `VISUAL_LABEL_TO_CODE` — обратный маппинг «описание → код»;
- `HARD_BLOCK_CATEGORIES` / `SOFT_REVIEW_CATEGORIES` — множества для движка решений.

Добавить новую категорию = добавить один `CategorySpec`, всё остальное
подтянется автоматически.

## 4. Конфигурация (`config.py`)

`Settings` — это `frozen dataclass`, который читает переменные окружения **один
раз при импорте**. Все фичи можно включать/выключать без правки кода:

| переменная | по умолчанию | что делает |
|------------|--------------|------------|
| `CENSOR_ENABLE_OCR` | `true` | включить OCR (в v2 не используется пайплайном) |
| `CENSOR_ENABLE_VISUAL_CLASSIFIER` | `true` | включить zero-shot классификатор |
| `CENSOR_ENABLE_EXPLICIT_DETECTOR` | `true` | включить NSFW-детектор |
| `CENSOR_ENABLE_POLICY_JUDGE` | `false` | включить ShieldGemma (консенсус-эвристика работает всегда) |
| `CENSOR_BLOCK_THRESHOLD` | `0.85` | порог блокировки |
| `CENSOR_REVIEW_THRESHOLD` | `0.55` | порог ручной проверки |
| `CENSOR_VISUAL_MODEL_ID` | `openai/clip-vit-base-patch32` | модель классификатора |
| `CENSOR_EXPLICIT_MODEL_ID` | `Falconsai/nsfw_image_detection` | модель NSFW |
| `CENSOR_POLICY_JUDGE_MODEL_ID` | `google/shieldgemma-2-4b-it` | модель-судья |
| `CENSOR_HF_CACHE_DIR` | `<проект>/.cache/huggingface` | куда качать веса |
| `CENSOR_TESSERACT_CMD` | автопоиск | путь к бинарю Tesseract |

`_default_tesseract_cmd()` сам ищет Tesseract: сначала в `PATH`, потом в типовых
путях Windows/macOS/Linux.

> ⚠️ Так как настройки читаются на уровне определения класса при импорте,
> менять переменные окружения «на лету» в одном процессе бесполезно — нужно
> перезапускать. Это нормально для сервиса, но об этом стоит помнить в тестах.

## 5. Сенсоры (адаптеры) — `adapters/`

Все адаптеры устроены по одному паттерну: **ленивая загрузка модели + единый
возврат `SignalResult` + защита от падений**.

### 5.1 `text_stub.py` — текстовый гард (ОТКЛЮЧЁН в v2)
Заглушка-контракт текстового гарда. В v2 **не подключена к пайплайну**: модуль
сфокусирован на изображении, текстовая проверка отложена (см. PLAN.md, P0.1).
Файл оставлен для будущего возврата.

### 5.2 `ocr.py` — извлечение текста из картинки (ОТКЛЮЧЁН в v2)
Через `pytesseract` (обёртка над Tesseract) вытаскивает строки текста. В v2 **не
вызывается из пайплайна** — OCR отложен вместе с текстовым гардом. Файл и его
зависимость (`pytesseract` в `requirements-ml.txt`) сохранены на будущее.

### 5.3 `visual_classifier.py` — zero-shot классификатор
По умолчанию `CLIP`. Модель не обучалась на наших категориях: мы передаём ей
текстовые описания всех 11 категорий и просим оценить сходство картинки с каждым.

> **Критически важный нюанс.** Zero-shot softmax-ит оценки по всем переданным
> меткам — они в сумме ≈ 1.0. Значит, у любой картинки (даже котика) всегда
> будет «самая вероятная» категория нарушения. Абсолютные значения здесь — это
> **относительное сходство среди наших меток, а не вероятность опасности**.
> Поэтому пороги 0.55/0.85 к этим оценкам применять напрямую некорректно — это
> главный источник будущих ложных срабатываний. См. PLAN.md.

### 5.4 `explicit_detector.py` — NSFW-детектор
По умолчанию `Falconsai/nsfw_image_detection`. В отличие от zero-shot — это
нормальная обученная модель `image-classification` с откалиброванными
вероятностями по своим меткам (`normal` / `nsfw`). Берём максимум среди меток,
содержащих маркеры `nsfw/porn/hentai/sexy/explicit`, и кладём в категорию
`sexual`. Это самый надёжный сенсор в текущем наборе.

### 5.5 `policy_judge.py` — слой арбитров (`role="judge"`)
Фасад `PolicyJudgeFacade` в v2 запускает арбитров **не «или-или», а вместе** и
возвращает список сигналов:

- **`ShieldGemmaJudge`** — настоящий мультимодальный судья на базе
  `google/shieldgemma-2-4b-it` (`ShieldGemma2ForImageClassification`). Грузится
  лениво по тому же паттерну, что и остальные ML-адаптеры. Мы отдаём ему наши
  **hard-категории** как кастомные политики (их описания из `taxonomy`) и берём
  вероятность нарушения по каждой. Включается через
  `CENSOR_ENABLE_POLICY_JUDGE=true`; при выключении/недоступности — `skipped`,
  и конвейер опирается на эвристику. Это сильный *независимый* сигнал, поэтому он
  участвует и во фьюжне (max), и как подтверждение.

- **`HeuristicPolicyJudge`** — работает **всегда**. Его единственная задача —
  давать `DecisionEngine` подтверждение (gate) для soft-категорий. Логика:
  - подтверждает категорию **только при консенсусе ≥2 независимых сенсоров**;
  - эмитит при этом **вторую по величине** оценку (уровень согласия), а не
    глобальный максимум — максимум и так считает `DecisionEngine`, дублировать
    незачём, и эта величина никогда не превышает max, поэтому ничего не «накручивает»;
  - категории, которые увидел лишь один сенсор, **не подтверждает** — для
    soft-категорий это и есть гашение шума (дойдут максимум до review, но не до block).

> **Почему так, а не как в MVP.** Прежняя эвристика пересчитывала глобальный
> `max` по категориям (дублируя движок) и для одиночных soft-категорий вычитала
> `−0.05`. Но движок берёт `max` по всем сигналам, включая исходный сенсор с
> непониженной оценкой, — поэтому `−0.05` был мёртвым кодом: он ничего не гасил,
> а лишь добавлял арбитра в источники категории и тем самым, наоборот, *разрешал*
> soft-блок. В v2 гашение реализовано через подтверждение по `role`, а не через
> арифметику оценок.

## 6. Движок решений (`decision.py`)

Финальный и самый важный шаг. Алгоритм:

1. **Сводим оценки.** По всем `ok`-сигналам для каждой категории берём
   **максимальную** оценку (`category_scores`) и запоминаем, кто её поднял
   (`category_sources`). Параллельно собираем `judge_confirmed` — множество
   категорий, названных хотя бы одним сигналом с `role="judge"`.
2. **Hard-блок.** Любая hard-категория с оценкой `≥ block_threshold` → блок
   (подтверждение арбитра не требуется).
3. **Soft-блок.** Soft-категория блокируется только если оценка `≥ block_threshold`
   **и** категория есть в `judge_confirmed` (её подтвердил любой арбитр —
   ShieldGemma или консенсус-эвристика). Так одиночный шумный сенсор не заблокирует
   «мягкую» категорию. Проверка идёт по `role`, а не по жёстко зашитому имени.
4. **Review.** Всё, что `≥ review_threshold`, но не дотянуло до блока → ручная проверка.
5. **Иначе** → `allow`.

`confidence` = максимальная оценка среди сработавших категорий (для `allow` —
максимум вообще, как «насколько близко подошли к границе»). `evidence` показывает,
какие именно сенсоры подтвердили каждую сработавшую категорию.

> Обратите внимание: **`scenario` и `stage` сейчас на решение не влияют** — они
> просто прокидываются в ответ. То есть проверка input и output по сути
> одинаковая. Это место для будущей дифференциации политик.

## 7. Точки входа

### HTTP API (`app.py`)
FastAPI с двумя ручками:
- `GET /health` → `{"status": "ok"}`;
- `POST /v1/moderate` → принимает `ModerationRequest`, возвращает `ModerationResponse`.

`pipeline = GuardrailPipeline()` создаётся **один раз** при старте — модели
шарятся между запросами.

> ⚠️ Ручка `moderate` **синхронная**, а инференс моделей — тяжёлый и
> блокирующий. Под нагрузкой это заблокирует event loop FastAPI. См. PLAN.md.

### CLI (`cli.py`)
`python -m censor_guard.cli --scenario output --image-path path/to.png`
Создаёт `GuardrailPipeline()` **на каждый вызов** и печатает JSON-ответ. Удобно
для локальной проверки одной картинки.

## 8. Зависимости

- `requirements.txt` — лёгкое ядро: FastAPI, uvicorn, pydantic, Pillow.
  Сервис **поднимется и без ML** — все ML-сенсоры просто будут `skipped`.
- `requirements-ml.txt` — тяжёлое: `transformers>=4.50` (нужен для
  `ShieldGemma2ForImageClassification`), `torch`, `accelerate`, `pytesseract`
  (на будущее, OCR в v2 не используется). Tesseract-бинарь ставится отдельно (это
  не pip-пакет). ShieldGemma-2 — gated-модель на Hugging Face: нужен доступ и
  `huggingface-cli login`.

Такое разделение позволяет гонять каркас/тесты быстро, а ML подключать по мере
надобности.

## 11. Главные ограничения текущей версии (честный список)

1. **Текст и OCR отключены в v2** — модерируется только изображение; промпт и
   текст внутри картинки пока не проверяются (см. PLAN.md, P0.1).
2. **Zero-shot оценки не откалиброваны** — softmax по меткам делает абсолютные
   пороги ненадёжными (риск ложных срабатываний/пропусков).
3. **ShieldGemma требует ресурсов и доступа** — 4B-модель gated на HF и по
   умолчанию выключена; без неё работает консенсус-эвристика.
4. **`stage`/`scenario` не влияют на политику** — input и output проверяются одинаково.
5. **API синхронный** — тяжёлый инференс блокирует event loop.
6. **Тесты покрывают движок и эвристику** — сенсоры/пайплайн/API ещё нет.
7. **Нет логирования/метрик/аудита** — невозможно разбирать инциденты пост-фактум.

Что с этим делать — расписано в [PLAN.md](PLAN.md).
